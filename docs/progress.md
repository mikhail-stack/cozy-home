Смена роли вступает в силу не позже чем через 15 минут (access-токен несёт роль; refresh перечитывает её из БД), удалённый пользователь не сможет обновить сессию, но действующий access-токен работает до истечения. Тесты: +32 (293 в backend, прежние без правок). Заодно после перезагрузки ПК пришлось вручную запустить Docker Desktop и `docker compose up -d postgres` — тесты бэкенда без Postgres падают с `ECONNREFUSED`
- **Пункт плана 21: Telegram-бот (`backend/src/modules/telegram/`).** Сделано: уведомление админа о новом заказе (формат ТЗ, раздел 8 — проверено тестом на дословное совпадение с примером, время по Киеву, обрезка под лимит 4096 символов, отправка после коммита без `await`: сбой Telegram заказ не ломает); привязка Telegram по одноразовой ссылке (`POST /api/telegram/link`, `GET /api/telegram/status`, бот принимает `/start <токен>`); long polling внутри backend-процесса (`startPolling`, пауза 5 с при сбоях, корректная остановка по SIGINT/SIGTERM); без токена бот отключён, остальное API работает. **Два отступления от ТЗ — требуют решения пользователя.** (1) **`/link email` не реализован.** ТЗ (раздел 7) привязывает `chat_id` по email без подтверждения; так любой, кто знает чужой email, привязал бы свой Telegram к чужому аккаунту, запросил бы восстановление пароля и получил код — полный захват аккаунта (в пункте 22 это стало бы уязвимостью). Вместо этого привязка идёт из личного кабинета по одноразовой ссылке (токен 192 бита, в БД sha256, TTL 15 мин, одноразовый, один активный на пользователя; `chat_id` берётся из самого сообщения Telegram). Бот на `/link` объясняет, где привязывать. Побочное следствие: сценарий ТЗ «забыл пароль, Telegram не привязан → привязать через бота» не работает — без входа в аккаунт привязать Telegram нельзя (в пункте 22 для такого случая нужно решение: например, показывать «обратитесь к администратору»). (2) **Вместо `node-telegram-bot-api` — прямые вызовы Bot API через `fetch`** (`telegram.api.ts`, ~60 строк, два метода): отложенный из пункта «Prettier + первый `npm install`» вопрос про 13 уязвимостей `npm audit` (2 critical, 4 high — цепочка `request`) решён удалением библиотеки; остались 4 high, но уже не из бота: `deepmerge-ts` (CLI Prisma) и `mysql2` — инструменты разработки, не рантайм. Тесты: +53 (346 в backend, прежние без правок): формат сообщений, клиент API (в т. ч. токен не попадает в логи), привязка и защита от захвата по email, гонка двух чатов на один токен, цикл polling, уведомление о заказе. Реальную связь с Telegram не проверял: токена бота нет — нужны `TELEGRAM_BOT_TOKEN` (от @BotFather), `TELEGRAM_ADMIN_CHAT_ID` и `TELEGRAM_BOT_USERNAME` в `backend/.env`. Ограничения: отвязать или сменить Telegram нельзя (в ТЗ такого нет), кнопка «Привязать Telegram» в `/profile` появится в пункте 23
- **Пункт плана 22: восстановление пароля по email (`backend/src/modules/auth/`, `backend/src/lib/mailer.ts`).** Пользователь попросил реализовать восстановление через email и предложил на выбор: выслать настоящий пароль либо выслать форму нового пароля (2 поля с подтверждением). **Первый вариант технически невозможен**: пароль хранится только как bcrypt-хеш (необратимый), backend не хранит и не может восстановить исходный пароль — хранить его в открытом виде было бы отдельной уязвимостью. Выбран второй вариант, при этом переиспользован формат из ТЗ (раздел 7), где это уже «код + форма нового пароля», только канал — email вместо Telegram (тот же TTL 15 минут и те же тексты ошибок «Код устарел, запросите новый» / «Неверный код»). Эндпоинты: `POST /api/auth/forgot-password` (всегда отвечает одинаково, email не существует — ничего не отправляется и не создаётся, но ответ тот же — защита от перебора адресов магазина), `POST /api/auth/reset-password`. Код — 6 цифр (`crypto.randomInt`, равномерное распределение, в отличие от `Math.random()`), в БД (`PasswordResetCode`) только `sha256(userId + код)` — хеш привязан к пользователю, поэтому совпадение кода у двух разных людей не создаёт коллизию; до 5 неверных попыток, дальше код сгорает как просроченный (нужен новый запрос) — защита от перебора всех 1 000 000 значений. Письмо отправляется через новый `lib/mailer.ts` (nodemailer поверх SMTP; без `SMTP_HOST/SMTP_USER/SMTP_PASS` отправка тихо пропускается, как Cloudinary/Telegram до своих ключей) — реальная доставка не проверялась, нужен настоящий SMTP (например, Gmail-приложение или Mailtrap для разработки). Фронтенд: `/forgot-password` и `/reset-password` обновлены под новый сценарий (убраны инструкции по Telegram, добавлено поле email на `/reset-password` — ссылка из письма вела бы на неё); реальный вызов API — пункт 23, как и у остальных форм авторизации. Тесты: +25 backend (371 всего, прежние без правок), фронтенд без изменений (65, страницы ещё не на API). `docs/plan.md` (пункт 22) и решение про `/link email` (пункт 21) теперь согласованы: сценарий ТЗ «Telegram не привязан» для восстановления пароля больше не нужен — пароль восстанавливается через email независимо от Telegram
