# CLAUDE.md — правила работы над Cozy Home

Локальные правила для этого проекта. Дополняют (не заменяют) глобальные настройки — здесь только то, что специфично именно для Cozy Home.

## Документация — читать в первую очередь

- [docs/cozy-home-tz.md](docs/cozy-home-tz.md) — техническое задание: страницы, сценарии, роли, сущности БД.
- [docs/architecture.md](docs/architecture.md) — архитектура: структура папок, разделение frontend/backend, деплой.
- [docs/DESIGN.md](docs/DESIGN.md) — дизайн-система: цвета, типографика, компоненты, do's/don'ts.

Перед архитектурными решениями или вёрсткой — сверяться с этими файлами, а не придумывать заново.

## Дизайн-система (docs/DESIGN.md)

Действует третья версия системы — **Nornorm** (скандинавский шоурум мебели), заменила две предыдущие (монохромная «UY Studio», тёплая кремово-шалфейная) целиком.

- Все токены (цвета, типографика, spacing) вшиты в [frontend/app/globals.css](frontend/app/globals.css) блоком `@theme`. Новые токены не изобретаем — используем `--color-canvas-white/bone/ash/stone/graphite/ink/obsidian/cobalt-ink`, `--text-caption…display` с парным `--tracking-*`, `--spacing-4…160`. Радиусы не переопределяем — берём стандартные `rounded-lg` (8px) из Tailwind; кнопки/пилюли — `rounded-md` (6px, см. ниже, отступление от DESIGN.md).
- ⚠️ **Шкала spacing переопределена буквально в пикселях** (`--spacing-8: 8px`, а не дефолтный Tailwind-множитель 0.25rem) — значит `h-8`/`p-24`/`gap-16` и т.п. означают ровно 8px/24px/16px, а не 32px/96px/64px, как было бы из коробки. Доступные числа: 4, 8, 12, 16, 24, 32, 40, 48, 64, 112, 140, 160 — использовать только их, любое другое число (например `h-10`) не сгенерирует правило вообще (тихо ничего не даст). Реальный баг из-за этого уже был: `h-8 sm:h-10` на логотипе схлопнуло картинку до 8px вместо ожидаемых 32/40px.
- **Cobalt Ink (`#1e37a0`) — единственный цветной акцент**, используется строго для логотипа, primary-кнопок и активных состояний (например, активная пилюля фильтра). Нигде больше цвет не применяется — весь остальной интерфейс на серой шкале.
- Шрифт Lunar недоступен — заменён на Inter (`lib/fonts.ts`, веса 400/500/700). На каждом текстовом размере обязателен парный отрицательный tracking (сигнатура системы, -0.03em).
- Кнопки — `rounded-md` (6px; сознательное отступление от pill-формы `rounded-full` из DESIGN.md, решение принято в чате), двух видов: `primary` (заливка Cobalt Ink) и `ghost` (прозрачная, рамка Obsidian). Радиус синхронизирован во всех местах с хардкодом классов кнопок (Button.tsx, CartDrawer.tsx, CategoryFilter.tsx, Hero.tsx, forgot-password/page.tsx).
- Без теней нигде. Разделение блоков — через поверхности (Canvas White / Bone), не через рамки; hairline-рамки (`border-ash`/`border-graphite`) допустимы только в функциональных списках/таблицах (корзина, админка), не на маркетинговых блоках.
- Логотип — реальный файл `frontend/public/logo.png` (не токен-дизайн из файла): цвет не перекрашивать под Cobalt.
- Компонентов Input/Modal/Select в файле дизайна нет (Nornorm — сайт без форм) — их стиль экстраполирован из общей системы (Ash-поверхность, `rounded-lg`, фокус Cobalt Ink) и не описан буквально ни в одном компоненте DESIGN.md.

## Технические конвенции

- **Backend** организован по доменам: новая сущность = новая папка `backend/src/modules/<domain>/` с `*.routes.ts`, `*.controller.ts`, `*.service.ts`. Не размазывать логику по техническим слоям (`controllers/`, `models/` на весь проект).
- **Frontend**: состояние — только в Zustand-сторах (`frontend/store/`), без Redux/Context для глобального state. Компоненты раскладываются по доменам в `frontend/components/*` (`catalog/`, `cart/`, `product/`, `layout/`, `ui/`).
- Tailwind v4 конфигурируется только через `@theme` в `app/globals.css` — отдельный `tailwind.config.js`/`.ts` не создаём (см. `docs/DESIGN.md` — источник токенов).
- Вся коммуникация фронта с бэкендом — через единую обёртку `frontend/lib/api.ts` (авто-подстановка токена, авто-refresh при 401). Прямых `fetch` из компонентов избегать.
- После правки `backend/prisma/schema.prisma` — прогонять `npm run prisma:migrate` в `backend/` и коммитить сгенерированную миграцию.
- Гостевая корзина — только `localStorage` (Zustand persist), серверная `CartItem` — только для авторизованных пользователей. Не путать эти два пути.
- Telegram-бот — часть `backend` (`src/modules/telegram`), отдельным процессом/сервисом не выносить.
- Монорепо без workspaces (npm/pnpm workspaces, Turborepo и т.п. не используем) — `frontend/` и `backend/` полностью независимы, каждый ставится и собирается отдельно.
- В обоих пакетах настроен Prettier (`.prettierrc.json`, `.prettierignore`) — перед коммитом прогонять `npm run format` в изменённом пакете; `eslint-config-prettier` уже отключает конфликтующие стилистические правила ESLint.
- В обоих пакетах включён типизированный ESLint (`typescript-eslint` `recommendedTypeChecked` + `projectService`) — ловит реальные баги вроде забытого `await`/floating promises, не только синтаксис. Область действия — только файлы внутри `tsconfig.json` (`src/**/*.ts` в backend, `**/*.{ts,tsx,mts}` во frontend); корневые `*.config.mjs` под это не подпадают. При появлении `no-unsafe-*` ошибок на внешних API (`fetch`, `JSON.parse` и т.п.) — приводить тип явным `as`, а не неявным присваиванием.
- **Frontend**, unit/component: Vitest + React Testing Library (`docs/architecture.md`, раздел 8.1), лежат рядом с тестируемым файлом как `*.test.ts`/`*.test.tsx`, не в отдельной папке. Запуск — `npm test` (разовый, для CI) или `npm run test:watch`. `next/image`/`next/link` в тестах замоканы глобально в `vitest.setup.tsx` — не заводить дублирующие моки внутри отдельных тестов.
- **Frontend**, e2e: Playwright (`docs/architecture.md`, раздел 8.2), спеки в `frontend/e2e/*.spec.ts`. Запуск — `npm run test:e2e`; поднимает/переиспользует `npm run dev` на `:3000` сам (см. `playwright.config.ts`, `webServer`). Ключевые элементы (карточка товара, строка корзины, сумма) размечены `data-testid={...}` — у карточки с фото и десктопного/мобильного дублей `Header` несколько элементов с одинаковым accessible name/aria-label, добавлять новый `data-testid`, а не городить хрупкий CSS/XPath-селектор.
- **Написанные тесты — заморожены.** Правило из `AGENTS.md` ("при редактировании существующего функционала тесты не редактировать") распространяется на все уровни и является общим для проекта, не только для правок: тесты пишутся один раз вместе с функционалом и дальше только **запускаются** (`npm test`, `npm run test:e2e`) как регресс-проверка, без последующих правок и удаления. Новые тесты под новый функционал — можно и нужно; редактировать/удалять уже существующий тестовый файл — нельзя. Если существующий тест упал — это сигнал реальной регрессии в коде, чинить нужно код, а не подгонять тест под новое поведение. Единственное исключение — явное поведенческое изменение, для которого сам пользователь явно попросил поменять и тест; без такой явной просьбы тест не трогать даже при большом соблазне.
- **Backend**: Vitest (`docs/architecture.md`, раздел 8.3), `npm test` в `backend/`, нужен запущенный Postgres (`docker compose up -d postgres` из корня; имя проекта в `docker-compose.yml` задано явно — папка кириллицей). Интеграционные тесты идут в отдельной БД `<имя>_test` (создаётся в `test/global-setup.ts`), дев-базу не трогать. Тесты нового модуля (пункты плана 15+) пишутся **в рамках того же пункта**, не "потом": unit для сервисов, integration через `supertest` поверх `createApp()` и тестовой БД (уже установлен, образец — `src/modules/auth/auth.routes.test.ts`). Пункт плана не считается завершённым без тестов на свою ключевую логику.
- **Prisma 7**: `url` в `datasource` schema.prisma не поддерживается — connection string только в `backend/prisma.config.ts` и в driver adapter клиента (`src/lib/prisma.ts`). После правки схемы: `npm run prisma:migrate` в `backend/` и коммит миграции; сгенерированный клиент (`src/generated`) в git не идёт — после клонирования `npm run prisma:generate`.

## Прочее

- Секреты — только в `.env` файлах (см. `.env.example` в корне, `frontend/`, `backend/`), никогда не коммитить реальные значения.
